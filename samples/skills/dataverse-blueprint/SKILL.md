# Dataverse Blueprint — Data Model as Code

Turns a business process into a **blueprint** (`*.blueprint.yaml`): a single, reviewable file that is the source of truth for a Microsoft Dataverse data model. A bundled zero-dependency CLI (`scripts/dvbp.py`) then **validates** it against 30 architecture rules, **renders** the design document, **compiles** an ordered, idempotent Dataverse Web API deployment plan, **deploys** it into a solution, **exports** a live environment back into a blueprint and **diffs** them to detect drift.

The judgment of a senior Power Platform architect, applied by the model, and enforced by deterministic code — so a design is never "approved" just because it reads well.

---

## Before Starting

**Critical**: identify the **mode** from the request, then ask for the inputs that mode needs. If the user doesn't provide all details upfront, ask for the missing ones before proceeding (in a single message, not one question at a time).

| Mode | When | Needs |
|---|---|---|
| **Design** (greenfield) | "design the data model for…" | 1–6 below |
| **Deploy** | "create it in my environment", "deploy the model" | an existing blueprint + 7 |
| **Audit** (brownfield) | "review / audit my Dataverse", "what's wrong with our model" | 7 + publisher prefix to scan |
| **Evolve** | "add X to the model", "we need a new field" | an existing blueprint + the change |

1. **Process description** — what happens, who does it, in what order, which records are produced (a paragraph, transcript, BPMN export or the columns of the current Excel/SharePoint lists)
2. **Publisher** — name and prefix (2–8 lowercase alphanumerics starting with a letter). Never accept `new` or `crXXX` for production
3. **Personas and access** — roles that create, approve, read or administer data, and the segregation (business unit, region, client, team)
4. **Volume and integration** — approximate records per year and external systems that sync data. Defaults to "low volume, no integration"
5. **Consumers** — model-driven app, canvas app, Power Pages, Copilot Studio agent, Power BI / Fabric. Defaults to model-driven app + Power BI
6. **Language** — for display names and the design document (LCID, e.g. 1033 English, 3082 Spanish). Defaults to the user's language; schema names are always English-style ASCII
7. **Environment URL** — e.g. `https://contoso-dev.crm.dynamics.com`, and confirmation that the user is signed in with `az login` (or has `DATAVERSE_TOKEN` set) with System Customizer or higher. **Development environments only.**

If a detail is still missing after asking once, proceed and record it in `assumptions` / `open_questions` in the blueprint.

## Output Structure

Every mode produces files in the user's repository, next to each other:

```
dataverse/
├── <solution>.blueprint.yaml   # source of truth — the only file humans edit
├── <solution>.design.md        # generated by `dvbp render` (never edited by hand)
├── <solution>.plan.json        # generated by `dvbp compile`
└── <solution>.live.yaml        # Audit/Evolve only: generated by `dvbp export`
```

The design document has these sections, all generated: Summary · Assumptions & Open Questions (`[ASSUMED]` / `[DECIDE]`) · Mermaid ER Diagram · Table Catalog · Column Dictionary · Choices · Relationships with cascade · Alternate Keys · Security Matrix (C R W D A AT Asg Sh × depth) and column security · Solution & ALM · Build Checklist (from the plan) · Risks & Anti-patterns Avoided · Validation Report with score.

In chat, reply with: the score and grade, the ER diagram, the open `[DECIDE]` items, and the exact next command. Do not paste the whole document.

## Step 1: Decompose the Process (Design mode)

Apply [references/design-rules.md](./references/design-rules.md) — load it before modelling.

- Nouns with a lifecycle → tables. Descriptors → choices, unless business users maintain them or they carry attributes → org-owned catalog table
- Map every actor to `systemuser`, `team`, `contact` or `account` **before** inventing custom tables for people or companies
- Events and history → status reason + auditing, not "history" tables, unless each transition carries its own data
- Tag every table, column, choice and relationship with `source: process` (it traces to what the user said) or `source: assumed`

## Step 2: Write the Blueprint

Write `<solution>.blueprint.yaml` following [references/blueprint-spec.md](./references/blueprint-spec.md). Start from [examples/ehs-inspections.blueprint.yaml](./examples/ehs-inspections.blueprint.yaml) when the domain is similar. Decide and write down, for each element:

- **Tables**: ownership (cannot change later), primary name or autonumber, audit, `integrated: true` when synced
- **Columns**: the most specific type; every date with `behavior`; money as `currency`; PII flagged `pii: true`
- **Relationships**: `parental` only when the child is meaningless without the parent (one per child), `restrict` for master data, `referential` otherwise; explicit intersect table when an N:N carries data
- **Security**: one role per persona, least privilege, depth `U B P O`, Append on the child + AppendTo on the parent for every lookup a role sets, column security profiles for PII
- **ALM**: environment variables, connection references, `anti_patterns_avoided` with the *why*

## Step 3: Validate — and Fix Until Clean

Run:

```bash
python .github/skills/dataverse-blueprint/scripts/dvbp.py validate dataverse/<solution>.blueprint.yaml
```

- Every `error` must be fixed in the blueprint and re-validated. Iterate until the exit code is `0`
- Fix `warning`s unless there is a stated reason; record the reason in `anti_patterns_avoided` or `open_questions`
- `info` (DV029) items are assumptions: surface them to the user as questions
- Rule meanings and fixes: [references/rule-catalog.md](./references/rule-catalog.md)
- If you cannot run commands, apply the rule catalog manually and say the score was not computed

## Step 4: Render the Design Document

```bash
python .github/skills/dataverse-blueprint/scripts/dvbp.py render dataverse/<solution>.blueprint.yaml -o dataverse/<solution>.design.md
```

Then present the score, the Mermaid diagram and the `[DECIDE]` list to the user. **Stop and wait for approval** before Deploy mode — the design is a decision document.

## Step 5: Compile and Deploy (Deploy mode)

```bash
python .github/skills/dataverse-blueprint/scripts/dvbp.py compile dataverse/<solution>.blueprint.yaml -o dataverse/<solution>.plan.json
python .github/skills/dataverse-blueprint/scripts/dvbp.py deploy  dataverse/<solution>.plan.json --env <URL> --check   # what exists / what would be created
python .github/skills/dataverse-blueprint/scripts/dvbp.py deploy  dataverse/<solution>.plan.json --env <URL> --apply   # only after explicit user confirmation
```

- `compile` refuses blueprints with validation errors
- The plan is ordered by dependency (publisher → solution → global choices → tables → columns → relationships → alternate keys → column security → roles → privileges → publish) and every step is idempotent (`exists_if` check, skip when present), so re-running is safe
- Every component is created with the `MSCRM.SolutionUniqueName` header, so it lands inside the solution
- Show the `--check` output and ask the user to confirm before `--apply`. Never run `--apply` against an environment the user describes as test or production; those get the **managed** solution through their pipeline
- After `--apply`, list the remaining `✋ manual` steps (formula columns are only creatable in the maker portal; status reasons; forms and views) and remind the user that alternate keys must reach **Active** before the first upsert
- Alternative path when the Dataverse MCP server is connected: you may create *simple* tables with its `create_table` tool, but relationships with cascade, alternate keys, column security and role privileges still go through the plan

## Step 6: Audit an Existing Environment (Audit mode)

```bash
python .github/skills/dataverse-blueprint/scripts/dvbp.py export --env <URL> --prefix <prefix> -o dataverse/<prefix>.live.yaml
python .github/skills/dataverse-blueprint/scripts/dvbp.py validate dataverse/<prefix>.live.yaml
```

- The export reverse-engineers custom tables, columns (with date behavior), global choices, alternate keys and custom N:1 relationships with their cascade behavior. Security roles are not exported; review them separately
- Report the score, then group findings into: **fix now** (errors that cause data loss or security exposure: DV005, DV008, DV011, DV014, DV023), **fix before the next release**, **accept with reason**
- For each finding say whether it can be changed in place or needs a migration (ownership, column type and table type changes need a new column/table + data migration)

## Step 7: Evolve and Detect Drift (Evolve mode)

- Edit the blueprint (never the environment first), validate, render, compile, deploy — the plan only creates what is missing
- To compare the repository with the environment: `dvbp export … -o live.yaml` then `dvbp diff dataverse/<solution>.blueprint.yaml live.yaml`. Lines starting `+` exist only in the environment (someone clicked in the portal), `-` only in the repo (not yet deployed), `~` changed, `!` breaking
- Offer the CI workflow in [ci/dataverse-blueprint.yml](./ci/dataverse-blueprint.yml): it validates every blueprint on each pull request and publishes SARIF so findings appear as inline annotations

## Rules

- **NEVER invent business requirements** — everything traces to the process (`source: process`) or is declared `source: assumed` and surfaced as a question
- **NEVER deploy without explicit confirmation**, never to test/production, and never with validation errors (`--force` exists for the user, not for you)
- **NEVER edit the generated `.design.md` or `.plan.json`** — change the blueprint and regenerate
- **NEVER create custom tables for users, teams, business units, accounts or contacts** when the standard table fits
- **NEVER use `new_` or `crXXX_` prefixes** in a production design
- Schema names: English, singular, `prefix_PascalCase`, ASCII. Display names: the user's language
- Explain **why** for every non-obvious decision (ownership, relationship behavior, choice vs lookup, depth)
- Prefer the simplest model that supports the process; push back on complexity without value
- Report only what the tools returned: if a command failed or was not run, say so; never claim a component exists in an environment without the `deploy` output showing it
- Respond in the same language the user writes in

## Examples

### Example 1: Design + deploy (greenfield)

**Input (user):**
> Our safety team inspects each plant monthly. Findings have a risk level and photo; each finding gets corrective actions assigned to an employee or a contractor (we must store the contractor's national ID). Plant managers only see their plant; the director sees everything. Plants come from our ERP. Prefix `cnt`. Deploy it to https://contoso-dev.crm.dynamics.com.

**Output (chat):**
> Blueprint written to `dataverse/EhsInspections.blueprint.yaml` and validated: **100/100 (A)**, 0 errors, 3 assumptions to confirm (City, Score, Estimated cost).
>
> *(Mermaid ER diagram)*
>
> **Decide before deploying:** 1) should closed inspections become read-only for inspectors? 2) retention for evidence photos.
>
> `--check` against contoso-dev: 35 steps would run, 0 components exist yet. Confirm and I'll run `deploy --apply`. After that, 3 manual steps remain (Days open formula column, inspection status reasons, forms/views).

Full files: [blueprint](./examples/ehs-inspections.blueprint.yaml) · [design](./examples/ehs-inspections.design.md) · [plan](./examples/ehs-inspections.plan.json).

### Example 2: Audit (brownfield)

**Input (user):** "Audit our Dataverse environment, prefix cr8a1."

**Output (chat, excerpt):**
> Score **0/100 (F)** — 14 errors, 25 warnings ([full report](./examples/legacy-tracker.report.txt)).
> **Fix now:** `cr8a1_Users` duplicates `systemuser` (DV005) · `cr8a1_Finding` is child of two parental relationships, so deleting a user cascades into findings (DV011) · `InspectorCedula` is PII without column security (DV014) · `InspectionDate` has no explicit behavior and will shift a day across time zones (DV008).
> **Needs migration:** `cr8a1_Inspections` is organization-owned, so plant segregation is impossible (DV023) — new user-owned table + data copy.

## Validation Checklist

Before presenting any design or audit, verify:

- [ ] `dvbp validate` exits 0 (or every remaining error is explained to the user as a blocker)
- [ ] Every `source: assumed` element and every `open_questions` entry is shown to the user
- [ ] The design document was regenerated from the final blueprint (score in its header matches)
- [ ] The Mermaid diagram matches the Relationships section (both are generated — do not hand-edit)
- [ ] Deploy ran `--check` first, the user confirmed, and the target is a development environment
- [ ] Manual steps and alternate-key index status were communicated after deploy
